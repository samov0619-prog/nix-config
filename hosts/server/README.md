# Сервер: обслуживание и обновление

Краткая памятка для человека. Полная установка, rescue, Disko и восстановление
доступа — в [SERVER_AI_INSTRUCTIONS.md](../../SERVER_AI_INSTRUCTIONS.md).

В командах `vps-current` — **SSH alias действующего NixOS-сервера**: пользователь
`samov`, порт `17431`, правильный SSH-ключ. Замени alias своим. Не путай его с
`vps-bootstrap` (временный Debian/rescue, root, обычно порт 22).
Команды выполняются **на рабочей машине в Fish**, если явно не сказано иначе.
`cd /home/samov/nix-config` — путь этого checkout; на другой машине замени его.

## Быстрые команды

| Задача | Команда с рабочей машины |
| --- | --- |
| Статус VPN | `ssh vps-current 'systemctl status wg-quick-awg0 --no-pager -l'` |
| Перезапустить VPN | `ssh vps-current 'sudo systemctl restart wg-quick-awg0'` |
| Статус DNS / AdGuard | `ssh vps-current 'systemctl status adguardhome --no-pager -l'` |
| Перезапустить AdGuard | `ssh vps-current 'sudo systemctl restart adguardhome'` |
| Последние ошибки VPN | `ssh vps-current 'sudo journalctl -u amneziawg-bootstrap -u wg-quick-awg0 -n 100 --no-pager'` |
| Последние ошибки DNS | `ssh vps-current 'sudo journalctl -u adguardhome -n 100 --no-pager'` |
| Неудачно запущенные службы | `ssh vps-current 'systemctl --failed --no-pager'` |
| Список клиентов | `ssh vps-current 'sudo awg-list-clients'` |
| Создать клиента | `ssh vps-current 'sudo awg-add-client phone'` |
| Удалить клиента | `ssh vps-current 'sudo awg-remove-client phone'` |

`phone` — пример имени: латинские буквы, цифры, `_` и `-`. Создание выводит QR с
секретом; не отправляй этот вывод в чат. Удаление отзывает доступ и удаляет файлы
профиля. Перезапуск VPN кратковременно отключает **всех** клиентов, но не должен
удалять их записи; счётчики трафика при этом обнуляются.

Если systemd сообщает `start-limit-hit`, сначала изучи и устрани исходную ошибку,
затем сбрось лимит и повтори запуск:

```fish
ssh vps-current 'sudo systemctl reset-failed amneziawg-bootstrap wg-quick-awg0'
ssh vps-current 'sudo systemctl restart wg-quick-awg0'
```

NaiveProxy обслуживает `caddy`, только если заданы `domain` и `acmeEmail`:
`ssh vps-current 'sudo systemctl restart caddy'`.

### AdGuard UI и скачивание профилей

```fish
ssh -N -L 8008:127.0.0.1:8008 vps-current
```

Оставь терминал открытым, зайди на <http://127.0.0.1:8008>; `Ctrl+C` закрывает
туннель. UI не выставлен в Интернет. DNS клиентов идёт на `10.66.0.1` через AWG:
исправный туннель ещё не означает исправный DNS.

```fish
sftp vpn-download@vps-current
```

В SFTP: `get phone.vpn` для AmneziaVPN или `get phone.conf` для native AWG.
Начальная папка уже `/files`, префикс `files/` не нужен. Оба формата и QR содержат
клиентский приватный ключ. Операторский SFTP-ключ даёт доступ ко всем профилям.

## Что делать после сбоя провайдера

1. Проверь SSH, затем статусы VPN и AdGuard из таблицы. Если SSH не работает,
   используй консоль провайдера: без связи перезапуск через SSH невозможен.
2. До перезапуска сохрани важные ошибки из журнала. Если пропали клиенты или
   файлы — сначала выполни диагностику следующего раздела и сделай копию состояния.
3. Проверь адреса, маршруты, место и файловую систему:

   ```fish
   ssh vps-current 'ip -br address'
   ssh vps-current 'ip route'
   ssh vps-current 'ip -6 route'
   ssh vps-current 'df -h / /var/lib/amneziawg /srv/vpn-download/files'
   ssh vps-current 'sudo journalctl -k -p warning -n 100 --no-pager'
   ```

   Сравни WAN и gateway с реальными settings и данными провайдера. Ошибки диска,
   read-only filesystem и отсутствие маршрута требуют отдельного исправления.
4. Если состояние на месте, перезапусти `wg-quick-awg0`, затем при необходимости
   `adguardhome`. Это не переустановка и не создание новых профилей.
5. Переподключи один существующий клиент. Проверь свежий handshake
   (`ssh vps-current 'sudo awg show awg0 latest-handshakes'`), открытие сайта и DNS.
   Нулевой timestamp означает отсутствие handshake; без попытки клиента его
   отсутствие ещё не доказывает поломку. Вывод содержит публичные ключи — не
   публикуй его целиком.

Потеря внешней сети сама по себе не равна остановке AWG. Статус службы не проверяет
доставку UDP через провайдера, NAT и DNS. Команды `status`, `awg` и
`awg-list-clients` не перезапускают службу. Если после просмотра статуса связь
вернулась, это ещё не доказывает, что её восстановила команда.
Не добавляем watchdog/restart-loop без установленной причины сбоя.

## Где живут клиенты и почему список может оказаться пустым

| Путь | Что содержит |
| --- | --- |
| `/var/lib/amneziawg/awg0.conf` | Серверный приватный ключ, HeaderProtectionKey и постоянные `[Peer]` с именами клиентов |
| `/srv/vpn-download/files` | Выданные `.conf`, `.vpn` и QR; это не база peers |
| `/var/lib/amneziawg/clients` | Сейчас не используется генератором; пустая папка нормальна |
| `/var/lib/private/AdGuardHome` | Изменяемое состояние AdGuard |
| `/var/lib/naiveproxy` | Секреты NaiveProxy, если включён |

В объявленной конфигурации корень — постоянный ext4, не tmpfs. Для AWG и профилей
не задана очистка по возрасту; Nix GC эти каталоги не обслуживает. Перезагрузка и
NixOS rollback не должны стирать клиентов, но **rollback поколения не восстанавливает
изменяемые данные из `/var/lib` и `/srv`**.

При запуске `wg-quick-awg0` зависимость `amneziawg-bootstrap` приводит поля
`[Interface]` к текущей схеме, сохраняя ключи и стандартные `[Peer]` из старого
конфига. Но если `awg0.conf` отсутствует, bootstrap автоматически создаёт новый
ключ и конфиг без клиентов. Он не может отличить первую установку от потери
состояния. Отсутствующие поля ключей тоже генерируются заново. Существующие файлы
профилей bootstrap не удаляет.

Это возможный механизм появления пустой базы после утраты файла, а не доказанная
причина конкретного инцидента. Если одновременно исчезли и peers, и опубликованные
профили, одного штатного bootstrap недостаточно для объяснения.

**Исправление переноса peers:** прежний bootstrap разбирал конфиг по абзацам
(`awk RS=""`). Без пустой строки перед `[Peer]` или со строкой из пробелов он мог
отбросить клиентские секции, сохранив оба серверных ключа и файлы выдачи. Теперь
перенос идёт по заголовкам секций; пустые строки нормализуются для совместимости
с командами списка и удаления. Исправление не восстанавливает уже потерянные peers.

Регрессионные тесты: `python3 -B hosts/server/tests/test_awg_state.py`. На старом
коде тест потери peer воспроизводит ошибку, исправленный скрипт сохраняет записи
с разными разделителями, имена и ключи при повторных запусках. Также проверены
список, удаление клиента и первая инициализация. Это локальные фикстуры с настоящими
Nix-generated скриптами и подменёнными AWG/openssl/chown, не проверка ядра/systemd
или действующего VPS. Формат файла до инцидента неизвестен, поэтому именно эта
причина потери старых клиентов остаётся гипотезой.

Чтобы применить исправление, сделай backup, затем выполни обычное обновление
**NixOS** по инструкции ниже; standalone HM для этого менять не требуется.
Изменение bootstrap применяется при его следующем запуске. После обновления
вручную перезапусти `wg-quick-awg0` (это отключит всех клиентов на время), проверь
список и подключение существующего профиля. Повтори перезапуск: клиенты и серверный
ключ должны сохраниться. Если активация NixOS уже перезапустила VPN, первый запуск
проверки уже произошёл; не считай, что switch гарантированно обошёлся без разрыва.

### Диагностика пропавших клиентов — до повторного запуска

Не удаляй конфиг, не запускай Disko и не создавай заново клиентов с теми же именами
до сохранения доступных данных. Выполни:

```fish
ssh vps-current 'sudo stat /var/lib/amneziawg/awg0.conf /srv/vpn-download/files'
ssh vps-current 'sudo ls -la /var/lib/amneziawg /srv/vpn-download/files'
ssh vps-current 'sudo rg -c "^\[Peer\]" /var/lib/amneziawg/awg0.conf'
ssh vps-current 'findmnt -T /var/lib/amneziawg'
ssh vps-current 'findmnt -T /srv/vpn-download/files'
ssh vps-current 'readlink -f /run/current-system'
ssh vps-current 'sudo journalctl --list-boots --no-pager'
ssh vps-current 'sudo journalctl -u amneziawg-bootstrap -u wg-quick-awg0 --since "2 days ago" --no-pager'
```

Расширь период под дату сбоя. `rg` без совпадений ничего не печатает и возвращает
код 1; ошибка чтения — не нулевое число peers. `rg` устанавливается серверным HM;
если его нет, не устанавливай инструменты ради диагностики, сообщи об этом.
Не выводи весь `awg0.conf`, клиентские конфиги или `awg showconf`: там секреты.
Журналы, имена файлов, адреса и ключи также просматривай перед отправкой.

Различай три случая:

- Файлы выдачи пропали, но `[Peer]` сохранились: существующие импортированные
  клиенты всё ещё могут работать. Серверный конфиг не хранит их приватные ключи,
  поэтому из него нельзя воссоздать прежние клиентские профили.
- `[Peer]` есть, но `awg-list-clients` пуст: команда показывает только записи с
  именем-комментарием и публичным ключом. Ручная перезапись/сохранение конфига могла
  убрать имена; пустая таблица сама по себе не доказывает отсутствие peers.
- `[Peer]` нет: это не доказывает исчезновение всего конфига. Могла быть потеряна
  только клиентская часть, в том числе из-за прежнего дефекта переноса peers.
  Сравни серверный публичный ключ с `[Peer].PublicKey` старого клиентского профиля;
  при совпадении обычная генерация новой серверной ключевой пары не подтверждается.
  Проверяй точную команду, VPS/диск, mounts, snapshots/restore, ошибки диска и
  время запуска bootstrap. Новые inode, `Birth` и `mtime` сами по себе не доказывают
  сброс: bootstrap заменяет файл через временный и при сохранении всех клиентов.

Для установления причины нужны точная команда, время инцидента, путь «очистившейся
папки» и состояние/журнал **того поколения, которое работает на VPS**, а не только
текущий код репозитория.

### Резервная копия AWG на рабочую машину

До дальнейших изменений сохрани доступное состояние вне VPS. На время копирования
не добавляй/удаляй клиентов и не перезапускай VPN; это копия файлов, не атомарный
snapshot работающих служб.

```fish
set backup_dir "$HOME/.local/state/nix-config/server-backups"
install -d -m 0700 "$backup_dir"
set backup "$backup_dir/awg-"(date -u +%Y%m%dT%H%M%SZ)".tar.gz"
ssh vps-current 'sudo tar -C / -czf - var/lib/amneziawg srv/vpn-download/files' > "$backup"
```

Проверь успешное завершение SSH/tar, затем:

```fish
chmod 0600 "$backup"
tar -tzf "$backup" > /dev/null
```

При ошибке это не подтверждённый backup; отсутствие исходных путей также означает
ошибку архивации. Архив содержит приватные ключи. Не клади его в Git, облако без
шифрования или чат. Храни отдельно также external settings, состояние AdGuard и
NaiveProxy. Проверка архива не заменяет пробное восстановление. Восстанавливать
нужно согласованную пару серверного конфига и профилей после остановки AWG, проверки
целевого VPS и сохранения его текущего состояния — не распаковывать вслепую поверх.

## Обновление существующего VPS

**Три разные операции:** получить свежий код (`git pull`), обновить версии
зависимостей (`nix flake update`), собрать и применить выбранную конфигурацию.
Ни update, ни verifier сами ничего не применяют к VPS. Пины локальных пакетов,
например AWG, не становятся новее автоматически от обновления nixpkgs.

1. На рабочей машине открой checkout. Проверь свои изменения; синхронизируй Git
   только после их сохранения/review. Если нужен именно текущий checkout, pull не
   требуется:

   ```fish
   cd /home/samov/nix-config
   git status --short
   git pull --ff-only
   ```

2. Найди **settings действующего VPS**. По умолчанию файл расположен в
   `$XDG_CONFIG_HOME/nix-config/server/settings.nix`, а без XDG override — в
   `~/.config/nix-config/server/settings.nix`. Он намеренно вне Git; пример
   `hosts/server/settings.nix` не является рабочей конфигурацией.
   Для следующих команд выбран обычный путь:

   ```fish
   set settings_dir "$HOME/.config/nix-config/server"
   test -f "$settings_dir/settings.nix"
   ```

   Если файла нет, сначала восстанови его из своей копии. Preflight может собрать
   проверяемые сетевые/дисковые данные, но не восстановит все прежние решения
   (домен, email и прочее) автоматически. Нельзя подставлять настройки нового
   провайдера для обновления старого сервера.
3. Сверь settings с `vps-current`: диск (`lsblk`), WAN, публичный IPv4, IPv6 VPN
   ULA (`ip -6 route`). При несовпадении остановись. Сделай off-host backup.
4. Обнови зависимости и собери только серверные NixOS и HM outputs:

   ```fish
   nix-flake-update-verify --hosts server --input all --server-settings "$settings_dir"
   ```

   Это настоящие локальные сборки, возможны расходы времени и диска. Для меньшего
   обновления вместо `all` укажи один input, например `nixpkgs`. После ошибки
   исправь причину; `flake.lock` автоматически не откатывается.
5. Просмотри `git diff -- flake.lock` и остальные изменения, результаты сборок,
   затем примени NixOS **самостоятельно**, сохранив SSH/консоль для восстановления:

   ```fish
   nixos-rebuild switch --flake /home/samov/nix-config#server --override-input server-settings "path:$settings_dir" --target-host samov@vps-current --sudo
   ```

   Не добавляй локальный `sudo`: сборка идёт на рабочей машине, `--sudo` повышает
   права только для активации на VPS. Локальный путь settings не записывается в
   lock. Для нестандартных путей с пробелами, `%`, `#` или `?` нужен URI encoding;
   verifier делает его сам, прямая команда выше предполагает простой путь.
6. HM применяется отдельно **на VPS** из того же проверенного commit/lock:

   ```fish
   cd ~/nix-config
   git pull --ff-only
   home-manager switch --flake "$HOME/nix-config#samov-server"
   ```

   Сначала обеспечь доступность проверенного commit в серверном checkout; pull не
   переносит незакоммиченные локальные изменения. Если `home-manager` ещё не
   установлен, используй bootstrap-команду из полной инструкции. HM не требует
   `server-settings` и не обновляет системные VPN/DNS-службы.
7. Проверь новый SSH-вход, VPN, AdGuard, список прежних клиентов и связь с одного
   старого профиля. При обновлении ядра/AWG-модуля запланируй reboot с доступной
   консолью провайдера, затем повтори проверки: switch не заменяет загруженное ядро.

### Можно ли обновить lock до preflight/settings?

**Да.** Для обновления зависимостей не нужны данные VPS:

```fish
cd /home/samov/nix-config
nix flake update
```

Это обновляет общий `flake.lock`, не проверяет сервер и не означает готовность к
deploy. После подготовки settings сборка выполняется без нового обновления:

```fish
nix-flake-update-verify --hosts server --no-update --server-settings "$HOME/.config/nix-config/server"
```

А `nix-flake-update-verify --hosts server --input all` — связка update + build:
она намеренно проверяет наличие settings **до изменения lock**. Без конкретных
значений сеть, GRUB, NAT, endpoint и другие части итоговой системы не определены.
Это не техническое ограничение `nix flake update`, а защита комбинированной команды.
Linux `--hosts all` тоже включает server и поэтому требует settings; для одного
VPS полная матрица не нужна. Verifier не запускает preflight и не подключается к VPS.

## Новый провайдер / второй VPS

- Если это **дополнительный одновременно работающий VPS**, сейчас отдельного
  NixOS output для него нет. Сначала добавь отдельный host и независимый источник
  settings; не переключай один `server-settings` между двумя живыми серверами.
- Если это **замена старого VPS**, сохрани старые settings и off-host backup,
  спланируй переключение и не используй новые settings для deploy на старый alias.
- Порядок для установки: проверить прямую TCP/UDP-доступность кандидата → настроить
  временный root SSH → запустить preflight на рабочей машине → проверить settings
  → собрать систему/Disko для этого target → установка → проверка сервисов и профилей.
  Команды и destructive gates — в
  [полной инструкции](../../SERVER_AI_INSTRUCTIONS.md#vps-installation).
- Preflight можно запустить из checkout, не устанавливая HM и не собирая сервер:

  ```fish
  cd /home/samov/nix-config
  nix shell nixpkgs#jq nixpkgs#openssh --command sh /home/samov/nix-config/hosts/server/preflight.sh vps-bootstrap
  ```

  Он читает inventory VPS по SSH, а settings записывает **локально и только после
  подтверждения**. Не запускает разметку/установку и не восстанавливает AWG-клиентов.
  Перед записью убедись, что не заменяешь настройки действующего сервера.

Для обычного обновления установленного NixOS **не нужны Disko и nixos-anywhere**.
