# Правила Common: пояснение AGENTS.md

Памятка для людей о том, что задаёт общий `AGENTS.md`. Это пояснение, а не ещё один файл инструкций для модели.

## Как это работает

OpenCode автоматически загружает `AGENTS.md` как общие правила поведения агента.
Он описывает подход к работе, но сам не выполняет команды и не создаёт новых агентов.
Проектные и личные инструкции дополняют эти правила.

Этот `agents.README.md` не подключён через `instructions` или `{file:...}` и не лежит в каталогах ролей, команд или скиллов. OpenCode не подхватывает его автоматически как инструкции. Имя отличается от `AGENTS.md` не только регистром, но и суффиксом — это важно для macOS.

При этом обычный README не скрыт от файловых инструментов: агент сможет прочитать его, если ему явно поручить или он откроет файл при исследовании репозитория.

## Основные правила

- **Выбор решений** (`Engineering Choices`). Сначала штатные возможности, поддерживаемые API и принятые в проекте подходы. Собственные обходы нужны только при конкретном ограничении; существенное усложнение согласуется с пользователем.

### Архитектурные принципы (Architecture Principles)

- **Простота:** минимальное решение текущей задачи, без абстракций и слоёв «на будущее».
- **Ответственность:** связанное поведение держать вместе, независимые задачи не смешивать.
- **Зависимости:** делать их явными, избегать циклов, скрытого общего состояния и неочевидных связей.
- **Контракты:** понятные интерфейсы, сохранение инвариантов и предсказуемая обработка ошибок.
- **Тестируемость:** по возможности отделять основную логику от ввода-вывода и внешних эффектов, без обязательных дополнительных слоёв.
- **Обобщения:** объединять одно и то же знание или правило, а не просто похожий код.
- **Масштаб изменений:** учитывать существующую архитектуру; локальная задача не разрешает перепроектирование. SOLID, FSD, конкретные папки и размер модулей не навязываются.

### Поиск, изменения и проверки

- **Поиск и чтение** (`Tools`, `Source Exploration`). Для поиска используются `glob` и `grep`, в shell — `fd` и `rg`. Агент читает нужные фрагменты, учитывает обрезанный вывод и проверяет источник до существенного вывода, включая комментарии, итог обсуждения и применимость к версии.
- **Вывод инструментов** (`Tool Output Selection`). Краткое представление удобно для навигации, но точные значения, код и ошибки проверяются по исходным данным.
- **Рабочие файлы** (`Working Files and Artifacts`). Полезные результаты сохраняются в подходящем месте; секреты не попадают в отчёты. Удалять можно только известные временные файлы текущей задачи, не чужую работу.
- **Форматирование и комментарии** (`Formatting`, `Code Comments`). Используется форматтер проекта только для изменённых файлов. Комментарии объясняют неочевидные причины и ограничения; посторонний cleanup не выполняется.
- **Проверки и ресурсы** (`Verification and Resources`). Ревью или просьба о коммите не разрешают сборку. Дорогие проверки требуют согласования; небольшие локальные тесты и статические проверки допустимы без него. В отчёте разделяются выполненные, невыполненные проверки, моки и реальная интеграция.
- **Следующие действия** (`User Actions`). Если действие остаётся пользователю, агент даёт короткий упорядоченный план.

## Требования при ревью

`Requirements Sources` требует проверять соответствие кода внешним требованиям, а не только предполагаемому замыслу автора.

Агент сначала использует указанную задачу или документ. Если их нет — ищет источник по выбранному MR или локальному диапазону через доступные read-only MCP XTracker, Wiki и GitLab. Проверяет связь задачи с ревизией, читает критерии приёмки и контракты; отдельная Wiki-страница нужна не всегда.

Если источник неоднозначен, агент уточняет его. Недоступное ТЗ — пробел покрытия, а не доказанная ошибка кода. Техническое ревью без внешнего ТЗ возможно по явной договорённости для этой задачи. Эти правила сами по себе не запускают отдельного reviewer.

## Работа с Git

`Git Workflow` запрещает агенту сетевые операции Git: синхронизацию выполняет пользователь.
Коммит создаётся только по отдельной явной просьбе, с ручным подтверждением (`Ask`, не `Always`).

Перед новой веткой или коммитом агент смотрит личную Git history и следует найденному стилю. Если номера задачи нет, спрашивает его, а не придумывает. Личный префикс Samov задаётся отдельно, не общими правилами.

## Лог задачи

`Task Log` работает только по явной просьбе «создай лог» или «обнови лог».
Агент загружает `task-summary-log` и пишет один краткий английский лог в `./promptLogs/` целевого проекта.
Ключ XTracker необязателен; дата берётся в UTC, секреты в лог не записываются.

## Где проходят границы

`AGENTS.md` — инструкции модели, не техническая песочница. Ограничения инструментов, провайдеров и Git дополнительно задаются в `opencode.jsonc` и плагинах. Личные роли и команды находятся в `opencode-local`, общая база от них не зависит.

Полный источник правил — [AGENTS.md](AGENTS.md); установка и настройки — [README.md](README.md).
