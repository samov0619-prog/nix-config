## Проверенные факты: discussion-map

- Дома устанавливается через `default.nix`, `programs.opencode.skills.discussion-map`.
  Живой файл `~/.config/opencode/skills/discussion-map/SKILL.md` существует,
  является HM-ссылкой; прочитан и совпадает по описанному поведению с исходником.
- В свежем `trf.zip` есть `opencode/skills/discussion-map/SKILL.md`. Корпоративный
  `opencode/AGENTS.md` дополнительно требует skill для установленных независимых
  веток разговора. Это свидетельство снимка, не проверка живого Mac.
- Домашние инструкции не содержат такого обязательного blanket-trigger.
- Текущий skill не explicit-only: описание разрешает вызов моделью, когда
  независимым темам действительно нужен раздельный учёт, или по просьбе пользователя.
  Шаги одной задачи, много сообщений или смена темы сами по себе не подходят.
- Отдельного программного детектора/фонового LLM-вызова у этого skill нет.
  Модель выбирает загрузку по описанию; отсутствие видимой карты не доказывает
  отсутствие загрузки: текст skill прямо запрещает повторять карту каждый ход.
- До загрузки на каждом модельном шаге рекламируются ID, имя и description,
  не все 60 строк Markdown. После загрузки тело становится частью разговора
  и может входить в следующие запросы до compaction/pruning. Это не означает
  одинаковую полную цену каждого хода: есть provider prompt caching.
- Значит, постоянный контекстный overhead объявления есть, но он мал относительно
  полного тела. Точные tokens/стоимость не измерялись; вызовы посчитаны ниже.
- Перевод в команду оправдан удобством явного управления, а не тем, что skill
  якобы умеет запускаться только явно. Нативного explicit-only skill уже достаточно
  для ручного использования без отдельной команды и дублирования текста.

## Справка для отдельных задач: provider-scoped MCP — вне текущего обновления

По решению пользователя эта тема не входит в согласование, реализацию и приёмку
текущего обновления. Исследование ниже сохранено только как справка для отдельных
задач; ни выбор гарантии, ни guard, ни разделение сред сейчас не требуются.
Существующие MCP-подключения и их настройки сохраняются без изменения поведения.

### Краткий вывод

Документированной настройки JSONC вида «этот MCP доступен только provider X»
не обнаружено в проверенных V2 guides. `mcp.use` и `provider.use` независимы,
условия по текущему provider в statement нет. Программный запрет выполнения
через поддерживаемый plugin API технически возможен; готового проверенного
guard для этих конфигураций пока нет. Это не основание обещать изоляцию данных.

### Что подтверждено в коде

- Исследован tag `v2.3.0`: `session.hook("context")` получает фактический
  `model.providerID` и позволяет менять outgoing tools/system/messages.
- `tool.hook("execute.before")` выполняется до прямого вызова и до вложенного
  инструмента внутри Code Mode. Типизированный `Tool.Error` останавливает вызов
  до executor. Это проверка кодом, не просьба к модели.
- Hook инструмента получает `sessionID`, `messageID`, `agent`, но **не model**.
  Для guard нужно установить provider именно породившего вызов assistant message,
  а не брать текущий mutable `session.model`: его могли переключить во время работы.
  В схеме assistant message есть model; связку получения через public API ещё
  необходимо проверить в реальном fixture. Неопределённая идентичность → отказ.
- Tool snapshot и Code Mode inventory фиксируются на запрос. Одного удаления
  прямых MCP tools из `event.tools` недостаточно: вложенные остаются в snapshot
  `execute`. Программный before-execution guard нужен и для них.
- Сравнены ключевые исходники `v2.1.4`: hook с отказом и путь вложенных Code Mode
  вызовов уже есть. Локальный `opencode --version` сообщает `v2.1.4+68bc26b`.
  Проверка tag не заменяет тест packaged runtime с местными patches/plugins.

### Три разные гарантии

1. **Запрет вызовов MCP tools от неподходящей модели.** Возможен server guard
   по точным server/tool ID и provider вызывающего сообщения. Проверять прямой
   вызов, Code Mode, детей, параллельные сессии, смену модели и отказ при неизвестном
   provider. Модель может попробовать запрещённое действие, но сервер его не выполняет.
2. **Скрытие MCP и всех его возможностей.** Дополнительно охватить Code Mode
   discovery/search, server instructions, resources и MCP prompts/commands.
   Простое скрытие tools или сравнение префикса не доказывает полноту. Нормализация
   имён должна быть однозначной; list всех resources тоже требует фильтрации.
3. **Никакие корпоративные MCP-данные не уходят другому provider.** Вызовной guard
   этого не даёт: история, ответы ребёнка, summary/compaction, файлы с выгрузками
   и title/generate могут уже содержать данные. После переключения provider
   запрещённый MCP не вызовется, но прежний ответ останется в контексте.

MCP transport соединяется с OpenCode, не с LLM-provider. Startup/initialize,
tools/list и административные MCP-вызовы могут происходить вообще без модели;
«не вызывать tools от provider X» и «не подключать сервер без provider Y» —
разные требования. Глобальное включение/выключение MCP при переключении одной
сессии не годится: несколько сессий могут работать с разными providers одновременно.

**Самый простой поддерживаемый вариант для строгого разделения:** отдельная
корпоративная среда/service с MCP и allowlist providers через native policies,
отдельные истории; другая среда без этих MCP. Это ограничивает свободное смешивание
providers, но не требует нового guard. Само разделение service не изолирует файлы,
секреты и сеть: при требовании полноценной security boundary нужна и средовая изоляция.

**Если нужно смешивание в одном процессе:** отдельный небольшой guard-plugin
через public API, не core patch. Это дополнительный поддерживаемый нами компонент
с обязательными regression tests. Его разработка пока не согласована.
Гарантия действует на покрытых путях OpenCode при загруженном доверенном guard;
не распространяется автоматически на произвольный shell HTTP/SDK или plugins,
которые сами ходят в сервисы. Provider ID также не доказывает доверенность endpoint.

### Skills, commands и личный review без симлинков

Skill — подгружаемая процедура: доступна модели по description или пользователю
через `@id`; autoinvoke можно выключить. Команда — явный `/name`, который подставляет
шаблон с аргументами в текущий разговор, если не настроено иное. Ни одна форма сама
по себе не выполняет детерминированный тест и не расширяет permissions.
Отдельный агент задаёт роль/system/model/permissions, а не способ хранения процедуры.

Автоматизация пайплайном не требует skill: установленный OpenAPI содержит
`POST /api/session/{sessionID}/command` (`session.command`, обязательны `name` и
`text`) и `GET /api/command` (`command.list`). Эти маршруты изучены, но выполнение
команд через них не проверялось. В `opencode run --help` установленной 2.1.4 нет
`--command`; такой CLI-синтаксис не предлагаем. Нативный skill отличается рекламой
description модели на каждом шаге и загрузкой через `skill`. Сам факт регистрации
команды не доказывает аналогичный автовызов моделью; дополнительный workflow или
интеграция может вызывать её явно. Это не причина добавлять skill-дубли.

Нынешние `delegated-review` и `delegated-review-chrome` уже **команды**, не skills.
Они остаются оркестраторами в текущей сессии (`subagent: false`, без command-level
`agent`/`model`): подготовка запускает настроенного `review` по существующему контракту.
Указывать `agent: review` на команде нельзя: это меняет выбранного агента/модель
вместо сохранения нынешнего родителя и управляемого запуска ребёнка.

Реализованное домашнее подключение: один личный `opencode-local/opencode.jsonc`, загружаемый
через `OPENCODE_CONFIG`; в нём `commands.<name>.template = "{file:commands/<name>.md}"`
и `agents.review.system = "{file:agents/review.md}"`. Metadata (`description`,
`subagent`, `mode`, `permissions`) задаётся JSONC, а подключаемые Markdown-файлы
содержат только тело, без YAML-frontmatter. Публичные имена, запреты reviewer,
review-policy paths и командные scope/recovery/privacy contracts сохраняются.
Относительные `{file:...}` разрешаются от JSONC; сам `OPENCODE_CONFIG` не является
discovery-каталогом для соседних agents/commands. Skills подключаются массивом
`skills` с `~/...` или абсолютным путём, не зависящим от рабочего проекта.

В Common личные команды/агенты не регистрируются: при выбранном личном overlay
они попадают в итоговую объединённую конфигурацию. Без overlay Common самостоятельный.
Существующие общие discovery-копии/симлинки убирать лишь после проверки новой
регистрации на целевых версиях; не удалять личные исходники. Живой Mac не проверен.
V2 commands/config guides и исходники 2.1.4/2.3.0 проверены; результат runtime ниже.

### U4. Compaction и стоимость — source-пути проверены, background оставляем

**Вывод:** у фоновой и обычной суммаризации один выбор модели и одна полноценная
задача сохранения состояния. Более дешёвая модель не гарантирует экономию или
сохранение качества. Новых настроек/моделей этот проход не добавляет.

Основание: [V2 compaction guide](https://opencode.ai/v2/docs/compaction) и исходники
тега v2.4.0/commit `44aed4fd144611879046ae923c25541f913780ad` из U3,
сопоставленные с нашим scratch stack и подготовленными домашними settings.
Это не проверка live config/credentials/metadata и не измерение тарифа или cache hit.

#### Какая модель действительно пишет summary

- `session/compaction.ts`: обычный `compact` вызывает `selectModel` (upstream:312),
  а `precompute` — тот же helper (:388), затем общий `summarize`.
  Background не имеет отдельной служебной роли/настройки модели.
  Это routing-роль выбора модели, не отдельный subagent: `prepare/baseTranscript`
  сохраняют context текущего агента, его system/tools/instructions; summary prompt
  добавляется к истории. Поэтому даже при той же модели hooks/prefix важны для cache.
- Наш `session-routing.patch` передаёт `{ kind: "compaction", agent: "compaction" }`
  в patched resolver даже без `agents.compaction.model`. Его приоритет:
  root metadata scoped override → role table `compaction`/`*` → переданная
  `agent.model` либо модель сессии. Поэтому штатная настройка
  `agents.compaction.model` сама по себе **не заменяет** модель заданного профиля.

| Подготовленный домашний source-config        | Выбор для новой summary   |
| -------------------------------------------- | ------------------------- |
| Нет routing profile и явной compaction model | Модель сессии             |
| Paid root profile без ручного override       | `openai/gpt-6.1-sol#high` |
| Free root profile без ручного override       | `opencode/big-pickle`     |

`summary` в `routing-models.json` — отдельная policy для session generate,
не роль compaction. Обычный helper-role выбор и request hooks — разные уровни:
`prepare` вызывает compaction hook от имени исходного session agent, сохраняя
его baseline/tools; summary template добавляется к запросу после hooks.
Это помогает сохранить prefix, но не является проверкой качества summary.
Таблица профиля уже хранится в root metadata: изменение JSON не обновляет старые
сессии автоматически. Для будущего модельного эксперимента нужны явно выбранный
профиль/overrides и проверка actual model; подробности остаются за U5.

#### История, лимиты и условия качества

- `keep.tokens = 15000` — недавняя история **рядом с результатом**, а не размер
  входа суммаризатору. Обычно он получает текущий checkpoint и последующую историю,
  включая сохраняемый хвост, а background — prefix до выбранного response anchor.
- В `v2-settings.nix` Sol/Luna имеют `context = 1050000`, `input = 244000`;
  native `inputWindow` берёт меньший положительный предел. При нашем
  `buffer = 32000` ceiling — **212000**. Background начинается за максимум
  60000 до ceiling, но на коротком цикле не раньше половины доступного интервала;
  **152000** — ориентир при достаточной длине цикла, не универсальный порог.
- Маленькое окно summary-модели может вызвать сокращение входа ещё до её ответа.
  `deliver → flattenAndDropOldest` сначала пробует подходящую неизменённую историю,
  затем text representation; сокращает старые exchanges по уровням, вплоть до
  пропуска целых старых обменов. Предыдущий checkpoint сохраняется, самый новый
  exchange может сокращаться, но не исключается целиком. После overflow есть
  дополнительные попытки уменьшения запроса; полнота текста этим не гарантирована.
- Output budget зависит от модели, свободного окна и provider hooks. Значение
  `SUMMARY_OUTPUT_FLOOR = 32000` не гарантирует 32000 доступных токенов вывода. Более того,
  `plugin/provider/openai.ts:335–341` штатно удаляет `maxTokens` для context и
  compaction запросов OpenAI; последующий `fitOutput` не восстанавливает его.
  Поэтому общий helper budget — не гарантированный output limit реального OpenAI.
- Finish reason `length` приводит к `compaction.failed`, а не молчаливому принятию
  оборванного ответа. Ответ без ожидаемых headings получает один nudge; проверка
  принимает наличие хотя бы одного heading, не проверяет смысловую полноту.
  Более слабую модель оценивать по сохранению требований, решений, точных путей/
  ошибок, незавершённой работы и правильному продолжению, не только по формату.

#### Кеш, удержанный summary и расход

- Background default — `true`; при `auto = false` или native compaction он
  пропускается. Он запускается около primary ceiling, проверяя свежесть primary
  response/model/variant; выбранная compaction model может быть другой.
  В исходниках default cache lifetime — **5 минут**, с margin **30 секунд**,
  либо TTL primary model. Это эвристика допуска, не подтверждение server-side hit.
- `session/model-request.ts:319–335` сохраняет cache affinity/key и передаёт TTL;
  исходный system/tools/history prefix по возможности не переписывается.
  При другой модели/провайдере на cache основной модели рассчитывать нельзя;
  при смене effort или hooks hit тоже нельзя обещать без измерения.
- Один background result удерживается в памяти на Session; при завершении scope/
  процесса теряется. При достижении порога OpenCode может ждать его завершения.
  `heldIndex/usePrecomputed` проверяют start/anchor и размер хвоста (до ~40% budget),
  но не writer model/Free-Paid профиль. Поэтому текстовый summary прежней модели
  может использоваться после переключения; новый Paid profile не гарантирует,
  что удержанный Free summary будет переписан. Это нативная переносимость текста,
  не нарушение routing нового запроса. После изменения истории/слишком большого
  хвоста summary отбрасывается и пишется заново.
- `background: false` останавливает будущие подготовки; его guard не очищает уже
  удержанную map и не является API отмены начатого запроса. Dynamic-toggle/in-flight
  поведение требует отдельного runtime-сценария; на свежем запуске такого held
  state нет. Не предлагать restart как обычный способ применить config.
- Usage публикуется для каждого завершённого модельного вызова как
  `source: "compaction"`, в том числе фонового; неиспользованный summary и повторные
  попытки могут стоить токенов. Финансовый расход/cache savings/качество здесь
  не измерялись; «дешевле за токен» не означает «дешевле за успешный checkpoint».

#### Отличия нашего патча от штатных гарантий

Исторические fixtures ниже выявили native identity gap. **Текущий production-патч
исправлен:** `native=true` сохраняет `context.model`, не вызывает helper routing;
отдельный durable fixture это проверяет. Текстовые summaries по-прежнему fail closed
при недоступной routed model. Native provider operation и semantic quality не проверены.

- Документация обещает fallback на модель сессии при неразрешимой agent model.
  В upstream helper есть `orElseSucceed`, а наш unconditional `models.resolve`
  его убирает. Source-fixture воспроизвёл это отличие; не обещать такой fallback
  домашнему routing и не вводить скрытую платную/межпровайдерную замену.
- Native upstream сохраняет модель сессии и не запускает background; её encrypted
  checkpoint переносится только на тот же provider/model. Наш helper может
  применить role routing **даже при native=true**, тогда как выбор native-ветки
  сделан по исходной модели. Fixture показывает замену Luna→Sol в таком условном
  входе. Реальная native provider operation не проверена; это несовместимость
  контракта локального патча, не доказанный live-сбой и не новая регрессия 2.4.0.
  В подготовленных settings native не включён. Не включать его в рамках переезда;
  перед отдельным включением сохранить native model identity и проверить сценарий.

**Решение пользователя:** оставить штатное поведение актуальной версии:
автокомпактация включена, background остаётся default `true`, без добавления
`compaction.background: false`. Сначала наблюдаем реальный расход; если он вырастет,
возвращаемся к отключению background. Возможная выгода — гипотеза, не измеренный
результат. Нынешние модели/профили сохраняются; более дешёвая модель остаётся
отдельным согласованным экспериментом. Числовой buffer этим решением не меняется.

- [x] Пользовательское решение: сохранить default background и наблюдать расход.
- Индикатор лимитов: убрать `Limits left`, `Checkpoint` и `week`, сохранив проценты,
  countdown, независимые предупреждения и `+`/`✓`. Один приглушённый `≋` показывает
