# Замечания и решения пользователя

[Каталог](README.md) · Обновлено: **09.11.2026**.

Отдельный журнал ревью, не сырая переписка. **Согласовано ≠ реализовано.**
Неоспоренную пометку агента не считаем выбором между вариантами: открытые решения
уточняем отдельно, небольшими порциями.

  lock: kernel 7.2.11, NVIDIA 615.78.08, Mesa 26.2.5, firmware 20260916. Input updates

  GPU power policy и живые тесты остаются открытыми; install guard сохранён.

- Пользователь уточнил: **`nodejs_latest` нужен на всех хостах с Node, без условий**,
  не только Lenovo. Предыдущий Lenovo-only selector удалён; общий Node module
  напрямую устанавливает `pkgs.nodejs_latest` для Acer/desktop/mac/Lenovo. Server
  его по-прежнему не импортирует; отдельной установки Node там не добавлено.
  Версии проектов при необходимости закрепляются в devShell/direnv. Это новейший
  major в выбранном nixpkgs snapshot, не гарантия LTS или совпадения с сегодняшним
  upstream. Текущий lock даёт **26.4.0**; lock не обновлялся. Mason остаётся
  менеджером инструментов; его установки и внешний Neovim config не менялись.
  [Сравнение источников](package-sources.md#nodejs-latest-общий-выбор).

  на Lenovo. Перечитан локальный Packwiz manifest: 38 mods, из них 9 client-only по
  декларациям; оптимизации соседствуют с worldgen, Tech Reborn и squaremap. Клиенту
  оставить расчёт Freesm и ручную корректировку при необходимости. Серверные `20G`

  памяти. Это исходная точка тестов, не разрешение включить instance/watcher или
  запускать сервер сейчас; config клиента/сервера не менялся.

- [Проверена основа графики Lenovo](graphics.md): доступны locked kernel 6.18.38,
  Mesa 26.1.4, linux-firmware 20260622 и NVIDIA 595.71.05. Upstream kernel/Mesa/NVIDIA

  живая проверка ThinkBook, итогового kernel config или firmware. PRIME/MUX,

  по требованию — пока рекомендация, не выбор пользователя. NVIDIA

- Пользователь выбрал начальный вход **как на Acer**: автологин, тот же публичный
  bootstrap-пароль пользователя для `sudo`, без Hyprlock. Перенесены только
  `getty.autologinUser`/`autologinOnce = true` (tty1 один раз за загрузку),
  `initialPassword` и обычная парольная аутентификация `sudo`. `mutableUsers = true`
  сохраняет будущую ручную смену пароля. Дополнительные группы Acer и trusted-users
  не перенесены. Fingerprint и улучшение входа отложены до живого Lenovo; PAM,
  отпечатки и idle locking не подключались. Сборки/activation/вход не проверялись,
  текущий пароль Acer не читался и не менялся. Блокер установки сохранён для железа

  вариант 50%/zstd и условия возврата при устойчивом давлении на RAM в обычной

  fixtures проверяют значения и подстановку `+10` в существующий HM prune script,
  но не исполняют очистку и не заменяют NixOS build/проверку на целевой машине.

- Пользователь явно подтвердил **ext4 для Lenovo** через выбор в форме. Вместе с
  предыдущими решениями: незашифрованный root ext4 и отдельный незашифрованный
  swap-раздел 48 GiB. Это совпадает с заготовкой; разрешения форматировать диск
  или устанавливать систему нет. Добавлены declaration asserts фактического

  и к swap 48 GiB. Существующая незашифрованная заготовка соответствует решению,

  операция с backup, при необходимости переустановкой, не обещание простой конверсии.

  датчик, Linux/PAM и fallback, ничего не включать сейчас. Отпечаток подтверждает

## FileManager1: локальный URI с localhost

- `localhost-uri.patch` нормализует только точный localhost authority без учёта

## Tofi и открытие текстовых файлов: ограниченная проверка

- На Acer/desktop/Lenovo задано `$menu = uwsm app -- $(tofi-drun)`;
  shared Tofi использует `terminal = "kitty --"`. Эта команда также приведена
  в [README pinned UWSM 0.26.4](https://github.com/Vladimir-csp/uwsm/blob/v0.26.4/README.md).
  Но [Tofi 0.9.1 drun_print](https://github.com/philj56/tofi/blob/v0.9.1/src/drun.c)
  печатает строку Exec, а не массив аргументов. Shell word splitting не разбирает
  полученные кавычки: валидное `fixture-app --label "two words"` превращается
  в два аргумента `"two` и `words"` вместо одного `two words`.
- Изолированная shell-проверка выполнила нынешнюю команду с fake Tofi/UWSM;
  ожидаемый argv подтверждён извлечённым tokenizer из pinned UWSM.
  Простой `kitty -- nvim` передаётся корректно. При отмене вызывается
  `uwsm app --` без команды, которую требует argparse UWSM; это не запуск
  приложения. Среди store-backed desktop entries установленного HM-профиля
  не найден Exec с проверенными символами кавычек/globbing. Ошибка сложных
  аргументов воспроизведена на fixture, не на установленном приложении;
  Tofi/UWSM пока не менялись. Весь desktop-entry contract этим не проверен.
- Selected merged HM evaluation пяти профилей подтвердила `neovim-unwrapped`
  и `EDITOR=nvim` везде; `text/plain = nvim.desktop`, Tofi и Kitty terminal
  — только на трёх GUI-профилях. Установленный Neovim 0.12.3 содержит штатный
  `nvim.desktop`: `Exec=nvim %F`, `Terminal=true`; desktop entry не отсутствует.
- Текущий installed xdg-utils 1.2.1 в generic-пути `search_desktop_file`
  не обрабатывает Terminal и запускает Exec напрямую. Текущая среда — Hyprland,
  portal override `NIXOS_XDG_OPEN_USE_PORTAL` не задан. Извлечённые настоящие
  функции installed `xdg-open`, копия пакетного `nvim.desktop` и fake nvim
  подтвердили прямой вызов без терминала, сохранив имя fixture с пробелами.
  Это отдельная проблема от запуска Neovim через Tofi: там терминал добавляет Tofi.
- Рекомендация для согласования: отдельный скрытый XDG-handler с
  `Terminal=false`, `Exec=kitty -- nvim %F` для `text/plain`; штатный пункт Neovim
  в Tofi, внешний конфиг редактора, Mason и CLI остаются прежними.
  Пока изменена только документация. Реальные Tofi, UWSM, Neovim, Kitty, D-Bus
  и пользовательские файлы не запускались; браузерные/clipboard/private данные
  не читались. Полная сборка и живая приёмка не выполнялись.

## Съёмные накопители: udiskie, UDisks2 и polkit

- Read-only source/declaration audit трёх GUI HM-профилей подтвердил udiskie
  2.6.2, automount/notifications включены, tray=`auto`, user service привязан
  к graphical-session/tray targets. Mac/server udiskie не включают. Waybar
  всех трёх GUI hosts содержит tray. Реальные службы/устройства не проверялись.
- `services.udiskie.settings.menu = "nested"` записывает `menu` в корень YAML,
  но installed `Config.program_options` читает только `program_options`.
  Поэтому этот setting игнорируется, действует upstream `menu=flat`.
  AST-extracted настоящий Config подтвердил это; in-memory контроль с
  `program_options.menu` распознаётся. В udiskie 2.6.2 `nested` также принимается
  как legacy alias `smart`; рекомендация — корректная секция с `menu="smart"`,
  если сохраняем заявленное намерение иерархического меню. Пока конфиг не менялся.
- Отсутствие HM `preferStatusNotifierItems`/CLI `--appindicator` не признано
  ошибкой: installed udiskie при tray + Wayland сам включает appindicator,
  если опция не задана; пакет включает GTK/libappindicator dependencies.
  Фактическая регистрация значка и rendering на Wayland не проверялись.
- Действие Browse по умолчанию использует `xdg-open`; AST-extracted настоящий
  `prompt.browser` с fake Popen подтвердил один неизменный аргумент каталога
  с пробелами/Unicode. Read-only `xdg-mime query default inode/directory`
  на Acer вернул `kitty-open.desktop`, чей package entry задаёт `kitty +open %U`.
  Installed Kitty 0.47.0 по умолчанию открывает shell с cwd каталога, не Yazi;
  в текущем Kitty config directory `*actions*` files не найдены, runtime не запускался.
  Общий `yazi-xdg.desktop` уже умеет `kitty -- yazi %f` и объявляет directory MIME,
  но явного default association `inode/directory` в GUI module нет.
  Предлагается согласовать его отдельно, не подменять это FileManager1:
  «Show in folder» по D-Bus и «открыть каталог» через MIME — разные входы.
- Выбранные NixOS declarations Acer/desktop/Lenovo: UDisks 2.11.1/polkit включены,
  mountOnMedia=false (upstream ACL-controlled `/run/media/$USER`). На Acer merged
  extra polkit rules относятся к NetworkManager/ModemManager, не blanket storage allow.
  Installed UDisks default policy разрешает обычный filesystem-mount активной
  локальной сессии, но system/other-seat mount требует admin authentication.
  Это privileged backend с пользовательским клиентом, не запуск Yazi от root.
- Отдельный authentication-agent не найден среди выбранных NixOS user service
  names и system package names; это coverage gap, не доказательство отсутствия
  runtime/ручного agent. HM/личный автозапуск и настоящие auth-dialogs полностью
  не обследовались. Polkit daemon сам по себе не гарантирует окно ввода пароля;
  правила и агенты не добавлялись без подтверждённой потребности.
- Устройства, mount/unmount/eject/power-off, D-Bus storage requests, auth prompts,
  сборки и activation не выполнялись. Android/MTP остаётся отложенным до Lenovo;
  legacy mount menu не возвращён. В этом шаге изменена только документация,
  применять NixOS/HM не требуется; две конкретные настройки предложены для согласования.

## MPV/Audacious: запуск и медиаассоциации

- Source audit: общий GUI set включает MPV через HM, Linux GUI set устанавливает
  Audacious. Сохранение обоих приложений уже согласовано; удаление или объединение

  mpv.conf/input.conf. Это не утверждение об отсутствии внешнего mutable config.
- Read-only queries шести MIME types на Acer: MP4/MKV/WebM → `mpv.desktop`,
  MP3 (`audio/mpeg`)/FLAC/OGG → `audacious.desktop`. Обработчики работают как GUI:
  installed package entries задают `Terminal=false`, соответственно
  `mpv --player-operation-mode=pseudo-gui -- %U` и `audacious %U`.
- Две изолированные проверки использовали настоящие desktop entries и извлечённые
  desktop-launch functions installed xdg-open с fake players. Сложное имя fixture
  с пробелами/Unicode/кавычками/literal shell characters передаётся одним аргументом,
  UID/EUID не меняются. Настоящие проигрыватели, звук, видео, сеть и GUI не запускались.

  не закреплён в конфигурации: fresh Lenovo не обязан повторить его автоматически.
  Предложение для согласования — явно сохранить видео → MPV, музыку → Audacious
  через конкретные MIME types, без wildcard-defaults и изменения личных настроек.
- Mutable playlists/history/watch-later и содержимое медиафайлов не читались;
  GPU decode, codecs, PipeWire и реальные playback controls не проверялись.

  считается успешной; затем выполнена только узкая Acer evaluation без builds/IFD.

Последующее решение по медиаассоциациям: оставить штатный выбор, без явных
audio/video MIME defaults и собственного полного перечня форматов. Пакетный
`MimeType` описывает поддерживаемые форматы, но не задаёт предпочтение между
несколькими приложениями. Если на Lenovo обнаружится реальное расхождение,
закрепить нужные исключения точечно. Сами проигрыватели сохраняются.

## Vulkan и RTX 5060

Laptop leaf включает Vulkan build Whisper.cpp и передаёт `-dev 1` — это GPU index
Acer. Для Lenovo проверить GPU/драйвер/перечисление устройств. Vulkan — кандидат;
CUDA/CPU сравнивать только по необходимости, с учётом задержки, сборки и батареи.
Работу конкретного Lenovo этим чтением не проверяли.

RTX 5060 относится к Blackwell: NVIDIA требует **open kernel modules**.
Не переносить Acer `open = false`; это не означает переход на Nouveau.
Ветку драйвера и power management выбрать отдельно.
Источник: [NVIDIA](https://us.download.nvidia.com/XFree86/Linux-x86_64/580.105.08/README/kernel_open.html).

## Swap, гибернация и обратимость

**Актуальное решение:** выбран swap-раздел **48 GiB**, размер задан в Lenovo scaffold.
По последним решениям root **ext4**, root и swap **без шифрования**, zram пока выключен.
Ниже сохранена история объяснений и
рассмотренных альтернатив; старые предложения swapfile не являются текущим выбором.

- Сон оставляет RAM под питанием; Linux swsusp сохраняет образ в активный disk swap,
  включая swapfile. До гибернации он работает как обычный swap.
- Образу нужны **свободные** slots: из 32 GiB swap при 6 GiB занятых остаётся 26 GiB.
  Образ не равен всему объёму RAM: cache можно отбросить, уже выгруженные страницы
  не дублируются как resident RAM, образ обычно сжимается. Размер зависит от нагрузки;
  правило swap=RAM не даёт безусловной гарантии.
- После resume место образа освобождается. Для одного образа нужна одна swap area:
  нельзя просто сложить размеры нескольких маленьких swapfiles.
- **Zram** хранит сжатые страницы в RAM, не резервирует весь logical size заранее.
  Экономия зависит от сжимаемости; сжатие/распаковка тратят CPU и могут замедлять
  при давлении на память, хотя часто быстрее disk swapping. Это не дополнительная
  физическая RAM и не место для гибернации. Включение/размер пока не выбраны.
- Предложение агента, **не согласованная разметка**: swapfile внутри зашифрованной
  root filesystem, чтобы менять размер без переразметки. При пересоздании проверить
  resume location/offset; у Btrfs свои ограничения. Альтернатива — заранее выделенная
  swap partition/LV. Fresh scaffold пока использует partition.
- Уточнение после вопроса пользователя: файл 10 GiB занимает примерно 10 GiB,
  дополнительные 20 GiB **не резервируются**. Рост до 30 GiB возможен только при
  наличии свободных 20 GiB на тот момент. Если заранее гарантировать этот запас,
  экономии перед сразу выделенными 30 GiB нет. Sparse file «на 30, занимает 10»
  не решение: обычный Linux swapfile не допускает holes.
- Пользователь уточнил, что свободное место для роста будет. «Без holes» не значит
  «один непрерывный участок диска»: файл может иметь несколько реально выделенных
  extents. Swapfile можно пересоздать большего размера при отключённом swap
  (нужна свободная RAM либо live-система) и обновить resume; переразметка и
  переустановка ОС для этого обычно не нужны. Для partition такой гибкости нет.
  Предложение сначала проверить сон/гибернацию Lenovo разумно; итоговая storage
  схема ещё не выбрана, тесты на устройстве не выполнялись.
  Для проверки hibernation уже нужен достаточно большой resume target и его
  настройка. После базовой установки можно использовать временный большой
  swapfile для тестов, затем подобрать постоянный размер без переустановки;
  filesystem/encryption лучше выбрать до установки.
- Практическая рекомендация на момент ревью (не универсальный стандарт «2026»):
  без hibernation 10 GiB — разумная исходная страховка для 32 GiB RAM, не гарантия
  против OOM. Для нужной hibernation выбрать больший target с запасом под уже
  занятый swap и проверить рабочие нагрузки. Swapfile даёт гибкость, не бесплатное
  место; большой swap сразу даёт предсказуемую ёмкость, но отнимает её у файлов.
- Сначала выбрать encryption/filesystem и обратимый способ изменения размера;
  затем проверить сон, battery drain и resume с GPU. Надёжность заранее не обещать.
  Во время hibernation нельзя менять сохранённые файловые системы из другой ОС;
  random-key-per-boot swap encryption не подходит для resume.

Источники: [Linux swsusp](https://docs.kernel.org/power/swsusp.html),
[swapfiles и resume](https://docs.kernel.org/power/swsusp-and-swap-files.html),
[NixOS power management](https://wiki.nixos.org/wiki/Power_Management).
Ограничения swapfile: [актуальный util-linux swapon(8)](https://man7.org/linux/man-pages/man8/swapon.8.html#NOTES).
Они объясняют механизм, не доказывают работоспособность Lenovo.

### Swapfile и partition: практическая разница

| Критерий              | Swapfile                                                                                                               | Swap partition                                                                                             |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Скорость на одном SSD | Обычно сопоставима: ядро обращается к выделенным блокам напрямую; фрагментация/нагрузка могут влиять, замера здесь нет | Простая фиксированная раскладка, но сама по себе не обещает заметного выигрыша                             |
| Изменение размера     | Пересоздать файл при отключённом swap и свободном месте, без переразметки                                              | Нужна работа с partition layout либо LVM; наличие свободного места в другой filesystem не расширяет раздел |
| Resume                | Нужно верно определить файл/offset и обновить настройку после пересоздания                                             | Проще: resume device без offset файла; достаточное свободное место всё равно требуется                     |
| Filesystem            | Ограничения выделения блоков; на ext4 проще. На Btrfs NOCOW/no compression, restrictions snapshots и balance/scrub     | Не зависит от root filesystem и её snapshots; encryption настраивать отдельно либо под общим LUKS/LVM      |

Оба варианта заранее занимают выделенный размер и не заменяют RAM. У файла нет
универсального существенного «налога за filesystem», но это не обещание равных
benchmark-результатов. Для ext4 file удобен; при Btrfs/snapshots partition часто
проще в сопровождении. По [Btrfs docs](https://btrfs.readthedocs.io/en/latest/Swapfile.html)
активный swapfile ограничивает не только snapshots своего subvolume, но и
whole-filesystem maintenance; отдельный subvolume не устраняет все ограничения.
При исходном сравнении filesystem/encryption ещё не были выбраны; последующими
решениями выбраны ext4 и отсутствие шифрования. Тип и размер swap согласованы.

### Последнее уточнение: большой раздел и ранняя проверка

- Пользователь уточнил SSD **1 TB** и предпочитает убрать дополнительную переменную
  swapfile из исследования стабильного resume. Готов выделить десятки GiB и сначала
  проверить сон/гибернацию; при отказе от неё рассматривает раннюю переустановку
  с меньшим swap. Затем явно согласован раздел 48 GiB; разрешение выполнить
  форматирование или установку из этого не следует.
- Принята рекомендация: **48 GiB swap partition для 32 GiB RAM**. Таблица
  [Red Hat Enterprise Linux 9, §15.2](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/9/html/managing_storage_devices/getting-started-with-swap_managing-storage-devices#recommended-system-swap-space_getting-started-with-swap)
  рекомендует для 8–64 GB RAM с гибернацией 1,5× RAM. Значение подтверждено
  индексированным текстом официального источника; прямое чтение страницы получило
  HTTP 403. Это общий ориентир другого дистрибутива, не стандарт NixOS и не
  гарантия любого workload. 48 GiB — около 51,5 GB, то есть 5,2% SSD на 1 TB.
- **«100% работающий запас» обещать нельзя:** имеют значение свободные swap slots,
  нагрузка, initrd/unlock/resume, firmware и драйверы. Размер раздела не исправит
  аппаратный resume. Swapfile сам по себе не нестабилен; раздел убирает именно
  сопровождение его offset и ограничения filesystem.
- Порядок: выбрать filesystem/encryption → установить базовую кандидатную систему
  с нужными kernel/NVIDIA stack и resume → рано проверить suspend и hibernate
  несколько раз на AC/батарее, в простое и с рабочими приложениями → решить,
  оставлять ли гибернацию. Неудача одной попытки требует диагностики, не доказывает
  невозможность на этом ноутбуке. До тестов сохранить работу; не монтировать
  сохранённые filesystem из другой ОС между hibernate и resume.
- Если от гибернации откажемся, до переноса данных переустановка с новой разметкой
  допустима как простой предсказуемый вариант. Она не обязательна: возможность
  вернуть место без неё зависит от расположения разделов и filesystem. Удаление
  swap-раздела само по себе не увеличивает root. Постоянный размер обычного swap
  ещё не выбран; вариант 8–10 GiB освободил бы примерно 38–40 GiB от предложенных 48.
- Этот вариант заменяет прежнее предложение использовать временный swapfile
  для тестов: файл возможен, но не нужен при проверке сразу с разделом.
  Размер 48 GiB уже согласован; последующим решением выбрано без шифрования.
  Затем явно выбран ext4 и начальная работа без zram, с условиями его включения позже.
